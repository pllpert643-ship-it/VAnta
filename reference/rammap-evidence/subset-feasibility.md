# Read-only memory subset feasibility

Status: design recommendation from VAnta source inspection, 2026-11-16. This note does not identify RAMMap implementation details or establish feature equivalence. Proposed interfaces and collection choices below are independently designed for VAnta; no RAMMap execution, EULA acceptance, REA calls, privilege changes, or application-code changes were performed for this note. Paths and line numbers refer to the inspected working-tree source and may move with concurrent edits.

## Reported implementation scope and feasibility

User-reported integration status: the local Memory Map UI now implements read-only Overview, Processes, and Process mappings views plus JSON snapshots. Backend implementation is in progress using psutil and GetPerformanceInfo, with no PFN queries, undocumented native queries, or Empty commands. This update records reported scope; this note has not independently verified the new implementation or its tests. The feasible subset therefore includes process virtual-memory mappings, with access-dependent coverage, but does not imply physical-page ownership or per-file cache residency. CSV remains an optional future extension. Keep collection independent of process-control actions and make coverage limits visible.

## Module interface and seam

As design guidance for the backend in progress, use a deep memory-observation module with a small interface, for example: `capture() -> MemorySnapshot`, plus a pure `serialize(snapshot, format) -> text` operation. These are proposed design choices, not observed RAMMap interfaces. Put collection, byte normalization, process-exit races, field availability, and warnings behind the collection seam. The UI owns refresh scheduling and destination selection; serialization performs no filesystem writes. A snapshot should carry capture start/end times because sequential process enumeration is not an atomic system-wide instant.

Reuse the existing `psutil.virtual_memory()`, process iteration/`memory_info()`, and optional `memory_counters()` collection patterns. Avoid constructing another `TaskManager` merely to obtain memory: its constructor opens/creates SQLite history (`src/vanta/infra/task_manager.py:79-85`) and sampling updates/commits usage history (`:177-195`), while also sampling unrelated hardware, disks, network, and GPUs (`:99-110,210-280`). A dedicated collector avoids those side effects and unrelated collection cost; an existing already-collected snapshot can instead be projected when available.

Represent unavailable per-field readings with `null` and a reason, rather than zero. Existing `ProcessRow` defaults memory/private to zero (`src/vanta/infra/task_manager.py:29-30`) and has one broad accessibility flag (`:43`); failures of unrelated getters also set that flag (`:141-155`). Consequently, neither zero nor `accessible=False` alone proves a memory measurement failed. A dedicated collector should retain field-level status; projection of existing rows must acknowledge this ambiguity. Retain denied-process placeholders and report skipped/exited processes without prompting for elevation. Use PID plus creation time for matching successive observations; do not merge rows by PID alone.

## Explicit exclusions

- **PFN and page-level mapping:** no physical page numbers, page-state/use-count matrix, per-page ownership, shared/private page decomposition, physical ranges, or claimed RAMMap-equivalent categories. The cited collectors supply aggregates and process counters, not evidence sufficient to build those views.
- **File cache attribution:** no per-file cached-page enumeration or cache ownership map. The existing aggregate `System cache` counter is useful but cannot by itself identify files or their resident pages.
- **Empty actions:** no working-set trimming, standby/modified-list clearing, cache purging, memory-pressure workloads, or memory-management configuration changes. Exclude process termination, priority, affinity, dumps, and other existing task-manager actions from this module's interface.
- **Driver and administrator path:** no driver installation/loading, kernel access, undocumented/native page enumeration, debug-privilege enablement, UAC relaunch, or administrator prerequisite. The design accepts partial observations under the current token; its scope deliberately avoids making elevated access a fallback requirement. Permission availability still needs verification on supported Windows versions.
- **Format compatibility:** export VAnta's documented snapshot schema, without claiming RAMMap snapshot compatibility or importing its artifacts.

## Acceptance checks for integration

Verify summary and optional-counter units, zero versus unavailable, process exit and PID reuse, partial access without elevation, stale-state handling, prevention of overlapping refreshes, and export of exactly the displayed snapshot. Test serialization with fixed snapshots and ensure private data beyond the intended name/PID/memory fields is not accidentally included through a whole-object dump. Verify the collector has no history/database writes or process-control calls. Existing `tests/test_task_manager.py:6-16` covers a real-process memory sample, and `:115` checks a Windows commit-limit reading; those are source-observed tests, not test results from this investigation, and do not establish the proposed subset's behavior.
